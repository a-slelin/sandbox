## 🧰 Перед началом

1. Настоящий набор сертификатов уже создан по [`HELP.md`](HELP.md): в папке `MutualTls/certs` лежат `ca.pem`,
   `ca.key`, `ca.srl`, `server.pem`, `server.key`, `client.pem`, `client.key`.
2. Модуль собран. Из корня репозитория `sandbox`:

```shell
mvn clean install -pl MutualTls -amd -am
```

3. Понадобятся **три окна терминала**:
   - **Терминал №1** — сервер, из корня репозитория `sandbox`;
   - **Терминал №2** — клиент, из корня репозитория `sandbox`;
   - **Терминал №3** — команды OpenSSL, из папки `MutualTls/certs`.

4. В терминале №3 перейдите в папку сертификатов (из корня репозитория `sandbox`):

```shell
cd MutualTls/certs
```

5. (Только Windows cmd) В каждом терминале включите UTF-8, чтобы кириллица отображалась нормально:

```bat
chcp 65001
```

Все «испорченные» наборы создаются в подпапке `MutualTls/certs/demo/` и не попадают в git (`.gitignore`).
Настоящие сертификаты в `MutualTls/certs` **не изменяются**.

## 🔌 Сценарий 1. Сервер не запущен

**Что проверяем:** клиент честно сообщает, что сервера нет, а не «зависает».

**1.1.** Убедитесь, что сервер **не** запущен (в терминале №1 ничего не работает; если работает — нажмите `Ctrl+C`).

**1.2.** В терминале №2 запустите клиента:

```shell
java -jar MutualTls/Client/target/Client.jar
```

**1.3.** В окне клиента нажмите **«Подключиться»**.

**Результат:** статус **«Ошибка подключения»**, красный замок, сообщение:

```text
Сервер недоступен — он запущен? (Connection refused: connect)
```

**1.4. Вариант с неверным портом.** В терминале №1 запустите сервер:

```shell
java -jar MutualTls/Server/target/Server.jar
```

В окне клиента в поле **«Порт»** укажите `9999` и нажмите **«Переподключиться»** — результат тот же: на порту
`9999` никто не слушает. Верните порт `8443`.

## 🏷️ Сценарий 2. Неверное имя хоста

**Что проверяем:** клиент сверяет хост, к которому подключается, со списком `subjectAltName` сертификата сервера
(`DNS:localhost`, `IP:127.0.0.1`). Сертификат подписан правильным CA, но выдан **не для этого имени** — значит,
это может быть чужой сервер.

**2.1.** Сервер запущен в терминале №1 (если нет):

```shell
java -jar MutualTls/Server/target/Server.jar
```

**2.2.** В окне клиента в поле **«Хост»** напишите `127.0.0.2` (это тоже ваш компьютер — весь диапазон
`127.x.x.x` ведёт на него же) и нажмите **«Подключиться»** / **«Переподключиться»**.

**Результат в клиенте:**

```text
TLS: имя хоста не совпадает с subjectAltName сертификата сервера
```

**Результат в журнале сервера:**

```text
[ОШИБКА] отказ в рукопожатии с /127.0.0.1:…: клиент отверг сертификат сервера
[ОШИБКА]     причина от JSSE: (certificate_unknown) Received fatal alert: certificate_unknown
```

**2.3.** Верните в поле **«Хост»** значение `localhost` — подключение снова проходит.

## 🚫 Сценарий 3. Клиент без сертификата

**Что проверяем:** главное отличие mTLS — сервер **требует** сертификат клиента. Подключимся «обычным» TLS-клиентом
OpenSSL, который сервер проверяет, а свой сертификат не отправляет.

**3.1.** Сервер запущен в терминале №1:

```shell
java -jar MutualTls/Server/target/Server.jar
```

**3.2.** В терминале №3 (папка `MutualTls/certs`) выполните:

```shell
openssl s_client -connect localhost:8443 -CAfile ca.pem
```

**Результат в терминале №3** (в конце вывода):

```text
… SSL routines … tlsv13 alert certificate required … SSL alert number 116
```

**Результат в журнале сервера:**

```text
[ОШИБКА] отказ в рукопожатии с /127.0.0.1:…: клиент не предъявил сертификат, выданный нашим CA
[ОШИБКА]     причина от JSSE: (certificate_required) Empty client certificate chain
```

**3.3. Для сравнения** — тот же OpenSSL, но с сертификатом клиента:

```shell
openssl s_client -connect localhost:8443 -CAfile ca.pem -cert client.pem -key client.key
```

Теперь сервер присылает `WELCOME Слелин Александр Владимирович (ПМИ-21МО)`. Введите `WHOAMI` и нажмите Enter —
сервер ответит, кто вы по сертификату. Выход — `Ctrl+C`.

## 🕵️ Сценарий 4. Сертификат клиента от чужого CA

**Что проверяем:** сертификат с **теми же** ФИО и группой, но подписанный не нашим CA, сервер не примет. Подделать
поля «кому выдан» может кто угодно — защищает именно подпись CA.

Сначала создадим «чужой» CA (он пригодится и в сценарии 7), затем сертификат клиента, подписанный им.

**4.1.** В терминале №3 перейдите в папку `demo`:

```shell
cd demo
```

**4.2.** Создайте ключ чужого CA:

```shell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out fake-ca.key
```

**4.3.** Создайте сертификат чужого CA (поля берутся из `fake-ca.cnf`: `CN = Чужой CA (Hacker CA)`):

```shell
openssl req -new -x509 -utf8 -config fake-ca.cnf -key fake-ca.key -days 30 -out fake-ca.pem
```

**4.4.** Создайте папку для поддельного набора клиента и перейдите в неё:

```shell
mkdir fake-client
```

```shell
cd fake-client
```

**4.5.** Создайте ключ клиента:

```shell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out client.key
```

**4.6.** Создайте запрос на сертификат с **настоящими** полями клиента (из `client.cnf`):

```shell
openssl req -new -utf8 -config ../../client.cnf -key client.key -out client.csr
```

**4.7.** Подпишите запрос **чужим** CA:

```shell
openssl x509 -req -in client.csr -CA ../fake-ca.pem -CAkey ../fake-ca.key -CAcreateserial -days 30 -extfile ../../client.cnf -extensions client_ext -out client.pem
```

**4.8.** Скопируйте настоящий `ca.pem` — клиенту он нужен, чтобы проверить сервер.

Windows (cmd):

```bat
copy ..\..\ca.pem .
```

PowerShell:

```powershell
Copy-Item ../../ca.pem .
```

Linux / macOS / Git Bash:

```shell
cp ../../ca.pem .
```

**4.9.** Убедитесь, что поля совпадают с настоящими, а издатель — чужой:

```shell
openssl x509 -in client.pem -noout -subject -issuer -nameopt utf8
```

Ожидаемый вывод:

```text
subject=C=RU, L=Ярославль, O=ЯрГУ им. П. Г. Демидова, OU=ПМИ-21МО, CN=Слелин Александр Владимирович, emailAddress=a.slelin.work@mail.ru
issuer=C=RU, O=Злоумышленник, CN=Чужой CA (Hacker CA)
```

**4.10.** Проверка через OpenSSL покажет, что наш CA этот сертификат не подписывал:

```shell
openssl verify -CAfile ca.pem client.pem
```

Ожидаемый вывод:

```text
… error 20 at 0 depth lookup: unable to get local issuer certificate
error client.pem: verification failed
```

**4.11.** Сервер запущен в терминале №1 (обычный, с настоящими сертификатами):

```shell
java -jar MutualTls/Server/target/Server.jar
```

**4.12.** В окне клиента в поле **«Сертификаты»** нажмите **«Обзор…»** и выберите папку
`MutualTls/certs/demo/fake-client` (или впишите путь и нажмите Enter). Карточка «Клиент» покажет красную метку
**«✕ не подписан ca.pem»**. Нажмите **«Подключиться»**.

**Результат в клиенте:**

```text
TLS: сервер требует сертификат клиента, подписанный его CA, а подходящего сертификата нет
```

**Результат в журнале сервера:**

```text
[ОШИБКА] отказ в рукопожатии с /127.0.0.1:…: клиент не предъявил сертификат, выданный нашим CA
[ОШИБКА]     причина от JSSE: (certificate_required) Empty client certificate chain
```

> Почему «не предъявил»: в начале рукопожатия сервер присылает список CA, которым доверяет. Java-клиент видит, что
> его сертификат выдан не из этого списка, и не отправляет его вовсе. OpenSSL отправил бы — и сервер ответил бы
> `PKIX path validation failed` (сертификат не подписан `ca.pem`). Результат один: доступа нет.

**4.13.** Вернитесь в папку `MutualTls/certs` (терминал №3):

```shell
cd ../..
```

## 🔑 Сценарий 5. «Левый» закрытый ключ клиента

**Что проверяем:** украсть **сертификат** недостаточно — он публичный, сервер его и так видит при каждом
подключении. Нужен ещё **закрытый ключ**. Возьмём настоящий `client.pem`, но подложим к нему чужой ключ.

**5.1.** В терминале №3 (папка `MutualTls/certs`) создайте папку и перейдите в неё:

```shell
mkdir demo/wrong-key
```

```shell
cd demo/wrong-key
```

**5.2.** Скопируйте **настоящие** `client.pem` и `ca.pem`.

Windows (cmd):

```bat
copy ..\..\client.pem .
```

```bat
copy ..\..\ca.pem .
```

PowerShell:

```powershell
Copy-Item ../../client.pem .
```

```powershell
Copy-Item ../../ca.pem .
```

Linux / macOS / Git Bash:

```shell
cp ../../client.pem .
```

```shell
cp ../../ca.pem .
```

**5.3.** Создайте **новый** закрытый ключ — он не пара к сертификату:

```shell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out client.key
```

**5.4.** Убедитесь, что открытые ключи различаются. Выполните две команды и сравните вывод — блоки между
`-----BEGIN PUBLIC KEY-----` и `-----END PUBLIC KEY-----` будут **разными**:

```shell
openssl x509 -in client.pem -noout -pubkey
```

```shell
openssl pkey -in client.key -pubout
```

**5.5.** В окне клиента выберите папку `MutualTls/certs/demo/wrong-key`. Карточка «Клиент» покажет
**«✓ подписан ca.pem»** (сертификат-то настоящий!) и красную метку **«✕ ключ не от сертификата»**. Нажмите
**«Подключиться»**.

**Результат в клиенте:**

```text
TLS: сервер отверг рукопожатие: подпись не сходится — закрытый ключ не от этого сертификата?
```

**Результат в журнале сервера:**

```text
[ОШИБКА] отказ в рукопожатии с /127.0.0.1:…: подпись клиента не сходится — его закрытый ключ не от предъявленного сертификата
[ОШИБКА]     причина от JSSE: (handshake_failure) Invalid CertificateVerify signature
```

> Как это работает: в сообщении `CertificateVerify` клиент подписывает данные рукопожатия своим закрытым ключом.
> Сервер проверяет подпись **открытым ключом из сертификата**. Ключи не пара — подпись не сходится.

**5.6.** Вернитесь в папку `MutualTls/certs`:

```shell
cd ../..
```

## ⏰ Сценарий 6. Просроченный сертификат клиента

**Что проверяем:** даже правильно подписанный сертификат с правильным ключом не примут после окончания срока.

**6.1.** В терминале №3 (папка `MutualTls/certs`) создайте папку и перейдите в неё:

```shell
mkdir demo/expired
```

```shell
cd demo/expired
```

**6.2.** Создайте ключ клиента:

```shell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out client.key
```

**6.3.** Создайте запрос с настоящими полями клиента:

```shell
openssl req -new -utf8 -config ../../client.cnf -key client.key -out client.csr
```

**6.4.** Подпишите его **настоящим** CA, но со сроком `-days 0` — сертификат истекает в момент выпуска:

```shell
openssl x509 -req -in client.csr -CA ../../ca.pem -CAkey ../../ca.key -CAserial ../../ca.srl -days 0 -extfile ../../client.cnf -extensions client_ext -out client.pem
```

(`-CAserial ../../ca.srl` — берём следующий серийный номер из счётчика настоящего CA.)

**6.5.** Проверьте даты — `notBefore` и `notAfter` совпадают:

```shell
openssl x509 -in client.pem -noout -dates
```

**6.6.** Скопируйте настоящий `ca.pem`.

Windows (cmd):

```bat
copy ..\..\ca.pem .
```

PowerShell:

```powershell
Copy-Item ../../ca.pem .
```

Linux / macOS / Git Bash:

```shell
cp ../../ca.pem .
```

**6.7.** Проверка через OpenSSL:

```shell
openssl verify -CAfile ca.pem client.pem
```

Ожидаемый вывод:

```text
… error 10 at 0 depth lookup: certificate has expired
error client.pem: verification failed
```

**6.8.** В окне клиента выберите папку `MutualTls/certs/demo/expired`. Карточка «Клиент» покажет красную метку
**«Недействителен»**, а журнал клиента — `Срок действия client.pem истёк — сервер его отвергнет`. Нажмите
**«Подключиться»**.

**Результат в клиенте:**

```text
TLS: сервер отверг сертификат клиента (подписан чужим CA или истёк срок) — подробности в журнале сервера
```

**Результат в журнале сервера:**

```text
[ОШИБКА] отказ в рукопожатии с /127.0.0.1:…: срок действия сертификата клиента истёк или ещё не наступил
[ОШИБКА]     причина от JSSE: (certificate_unknown) PKIX path validation failed: … validity check failed
```

**6.9.** Вернитесь в папку `MutualTls/certs`:

```shell
cd ../..
```

## 🎭 Сценарий 7. Поддельный сервер (сертификат от чужого CA)

**Что проверяем:** mTLS защищает **обе** стороны — клиент не станет общаться с сервером, сертификат которого
подписан не нашим CA (например, злоумышленник подменил сервер). Поля сертификата при этом настоящие и даже
`subjectAltName` правильный.

> Нужен `fake-ca.pem` / `fake-ca.key` из шагов 4.2–4.3. Если сценарий 4 не выполнялся — сначала выполните шаги
> 4.1–4.3, затем вернитесь в папку `MutualTls/certs` командой `cd ..`.

**7.1.** В терминале №3 (папка `MutualTls/certs`) создайте папку и перейдите в неё:

```shell
mkdir demo/fake-server
```

```shell
cd demo/fake-server
```

**7.2.** Создайте ключ поддельного сервера:

```shell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out server.key
```

**7.3.** Создайте запрос с **настоящими** полями сервера (из `server.cnf`):

```shell
openssl req -new -utf8 -config ../../server.cnf -key server.key -out server.csr
```

**7.4.** Подпишите его **чужим** CA (расширения — настоящие, включая `subjectAltName`):

```shell
openssl x509 -req -in server.csr -CA ../fake-ca.pem -CAkey ../fake-ca.key -CAcreateserial -days 30 -extfile ../../server.cnf -extensions server_ext -out server.pem
```

**7.5.** Скопируйте настоящий `ca.pem` — поддельному серверу он нужен, чтобы принимать настоящих клиентов.

Windows (cmd):

```bat
copy ..\..\ca.pem .
```

PowerShell:

```powershell
Copy-Item ../../ca.pem .
```

Linux / macOS / Git Bash:

```shell
cp ../../ca.pem .
```

**7.6.** Вернитесь в папку `MutualTls/certs`:

```shell
cd ../..
```

**7.7.** В терминале №1 остановите настоящий сервер (`Ctrl+C`) и запустите **поддельный**:

```shell
java -jar MutualTls/Server/target/Server.jar --certs=MutualTls/certs/demo/fake-server
```

В его выводе видно: `Кем выдан  Чужой CA (Hacker CA)`.

**7.8.** В окне клиента выберите **настоящую** папку `MutualTls/certs` и нажмите **«Подключиться»**.

**Результат в клиенте:**

```text
TLS: сертификат сервера не подписан нашим ca.pem
```

Карточка «Сервер» не заполняется — клиент не доверяет полученному сертификату и разрывает рукопожатие.

**Результат в журнале поддельного сервера:**


**7.9.** Остановите поддельный сервер (`Ctrl+C` в терминале №1).

## 🔀 Сценарий 8. Сервер с сертификатом клиента

**Что проверяем:** у каждого сертификата есть **назначение** (`extendedKeyUsage`). Сертификат клиента
(`clientAuth`) подписан настоящим CA, но для роли сервера (`serverAuth`) не годится.

**8.1.** В терминале №3 (папка `MutualTls/certs`) создайте папку:

```shell
mkdir demo/swap
```

**8.2.** Скопируйте сертификат и ключ **клиента** под именами сервера и настоящий `ca.pem`.

Windows (cmd):

```bat
copy client.pem demo\swap\server.pem
```

```bat
copy client.key demo\swap\server.key
```

```bat
copy ca.pem demo\swap\ca.pem
```

PowerShell:

```powershell
Copy-Item client.pem demo/swap/server.pem
```

```powershell
Copy-Item client.key demo/swap/server.key
```

```powershell
Copy-Item ca.pem demo/swap/ca.pem
```

Linux / macOS / Git Bash:

```shell
cp client.pem demo/swap/server.pem
```

```shell
cp client.key demo/swap/server.key
```

```shell
cp ca.pem demo/swap/ca.pem
```

**8.3.** В терминале №1 запустите сервер с этим набором:

```shell
java -jar MutualTls/Server/target/Server.jar --certs=MutualTls/certs/demo/swap
```

В выводе сервера: `Назначение  TLS-клиент (clientAuth)`.

**8.4.** В окне клиента (папка `MutualTls/certs`) нажмите **«Подключиться»** / **«Переподключиться»**.


**Результат в журнале сервера:**

```text
[ОШИБКА] отказ в рукопожатии с /127.0.0.1:…: клиент отверг сертификат сервера
[ОШИБКА]     причина от JSSE: (certificate_unknown) Received fatal alert: certificate_unknown
```

**8.5.** Остановите сервер (`Ctrl+C` в терминале №1).

## 🔁 Сценарий 9. Обрыв соединения и Reconnect

**Что проверяем:** статус соединения и кнопка Connect/Reconnect.

**9.1.** В терминале №1 запустите настоящий сервер:

```shell
java -jar MutualTls/Server/target/Server.jar
```

**9.2.** В окне клиента (папка `MutualTls/certs`, хост `localhost`, порт `8443`) нажмите **«Подключиться»** —

**9.4.** Снова запустите сервер в терминале №1:

```shell
java -jar MutualTls/Server/target/Server.jar
```

**9.5.** В окне клиента нажмите **«Переподключиться»** — статус снова **«Подключено · mTLS»**.
