## 🎯 Что получится в итоге

После всех шагов в папке `MutualTls/certs` появятся файлы:

| Файл          | Что это                                             | Кто использует                                   |
|---------------|-----------------------------------------------------|--------------------------------------------------|
| `ca.key`      | Закрытый ключ удостоверяющего центра (CA)           | Только вы — для подписи сертификатов на шагах 2–3 |
| `ca.pem`      | Сертификат CA (корень доверия)                      | Сервер и клиент — для проверки собеседника       |
| `ca.srl`      | Счётчик серийных номеров, OpenSSL создаёт его сам   | OpenSSL при выпуске следующих сертификатов       |
| `server.key`  | Закрытый ключ сервера                               | Сервер                                           |
| `server.pem`  | Сертификат сервера, подписанный CA                  | Сервер отправляет его клиенту                    |
| `client.key`  | Закрытый ключ клиента                               | Клиент                                           |
| `client.pem`  | Сертификат клиента, подписанный CA                  | Клиент отправляет его серверу                    |

Схема доверия:

```text
                    ┌──────────────────────────────────┐
                    │  ca.pem  «Слелин А. В. Root CA»  │  ← самоподписанный, подписан ключом ca.key
                    └───────────────┬──────────────────┘
                 подписывает ca.key │ подписывает ca.key
                 ┌──────────────────┴──────────────────┐
                 ▼                                     ▼
   ┌──────────────────────────────┐      ┌──────────────────────────────┐
   │ server.pem                   │      │ client.pem                   │
   │ Слелин Александр Владимирович│      │ Слелин Александр Владимирович│
   │ ПМИ-21МО · serverAuth        │      │ ПМИ-21МО · clientAuth        │
   │ SAN: localhost, 127.0.0.1    │      │                              │
   └──────────────────────────────┘      └──────────────────────────────┘
```

> ⚠️ Файлы `*.key` — это **секреты**. Они уже добавлены в `.gitignore` и не попадут в репозиторий. Никому их не
> отправляйте.

## 🧰 Шаг 0. Подготовка

**0.1. Убедитесь, что OpenSSL установлен и его версия — 3.x.**

```shell
openssl version
```

Ожидаемый вывод (цифры после `3.` могут отличаться):

```text
OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13 30 Jan 2024)
```

Если команда не найдена — добавьте папку `bin` из установленного OpenSSL в переменную среды `PATH`
(например, `C:\Program Files\OpenSSL-Win64\bin`) и откройте терминал заново.

**0.2. Перейдите в папку с конфигурациями сертификатов.**

Из корня репозитория `sandbox`:

```shell
cd MutualTls/certs
```

На Windows в `cmd` можно писать и через обратную косую черту:

```bat
cd MutualTls\certs
```

**0.3. Проверьте, что в папке лежат три конфигурационных файла.**

Windows (cmd):

```bat
dir *.cnf
```

Linux / macOS / Git Bash / PowerShell:

```shell
ls *.cnf
```

Должны быть видны: `ca.cnf`, `client.cnf`, `server.cnf`. Что в них написано — см. раздел
[Что написано в файлах .cnf](#-что-написано-в-файлах-cnf).

**0.4. (Только Windows cmd) Включите UTF-8 в консоли**, чтобы кириллица в выводе OpenSSL отображалась нормально:

```bat
chcp 65001
```

## 🏛️ Шаг 1. Корневой удостоверяющий центр (CA)

CA — это «доверенная третья сторона». Сервер и клиент не знают друг друга заранее, но оба доверяют CA. Если
сертификат собеседника подписан этим CA — ему можно верить.

**1.1. Создайте закрытый ключ CA** (RSA, 4096 бит):

```shell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out ca.key
```

| Часть команды                        | Что значит                                                            |
|--------------------------------------|-----------------------------------------------------------------------|
| `genpkey`                            | Создать закрытый ключ (результат — формат PKCS#8, который читает Java) |
| `-algorithm RSA`                     | Алгоритм ключа — RSA                                                  |
| `-pkeyopt rsa_keygen_bits:4096`      | Длина ключа — 4096 бит (для корня берут ключ подлиннее)               |
| `-out ca.key`                        | Куда сохранить ключ                                                   |

Во время генерации OpenSSL печатает строку из точек и плюсов — это нормально, так он показывает поиск простых чисел.

Проверьте, что файл начинается правильно:

Windows (cmd):

```bat
type ca.key
```

Linux / macOS / Git Bash / PowerShell:

```shell
cat ca.key
```

Первая строка должна быть ровно такой:

```text
-----BEGIN PRIVATE KEY-----
```

**1.2. Создайте самоподписанный сертификат CA** на 3 года (1095 дней):

```shell
openssl req -new -x509 -utf8 -config ca.cnf -key ca.key -days 1095 -out ca.pem
```

| Часть команды       | Что значит                                                                                  |
|---------------------|---------------------------------------------------------------------------------------------|
| `req -new`          | Создать новый запрос на сертификат                                                          |
| `-x509`             | Сразу выпустить из запроса **самоподписанный** сертификат (подписан своим же ключом)        |
| `-utf8`             | Читать значения полей как UTF-8 — нужно для кириллицы                                       |
| `-config ca.cnf`    | Взять поля «кому выдан» из секции `[ dn ]` и расширения из `[ ca_ext ]` файла `ca.cnf`      |
| `-key ca.key`       | Ключ, открытая часть которого попадёт в сертификат и которым сертификат будет подписан     |
| `-days 1095`        | Срок действия: 1095 дней = 3 года                                                           |
| `-out ca.pem`       | Куда сохранить сертификат                                                                   |

Вопросов OpenSSL не задаст: в `ca.cnf` указано `prompt = no`, все поля берутся из файла.

**1.3. Посмотрите, что получилось:**

```shell
openssl x509 -in ca.pem -noout -subject -issuer -dates -nameopt utf8
```

Ожидаемый вывод:

```text
subject=C=RU, L=Ярославль, O=ЯрГУ им. П. Г. Демидова, OU=ПМИ-21МО, CN=Слелин А. В. Root CA
issuer=C=RU, L=Ярославль, O=ЯрГУ им. П. Г. Демидова, OU=ПМИ-21МО, CN=Слелин А. В. Root CA
notBefore=…сегодняшняя дата…
notAfter=…дата через 3 года…
```

`subject` и `issuer` совпадают — значит, сертификат самоподписанный, как и должно быть у корневого CA.

Проверьте расширения CA:

```shell
openssl x509 -in ca.pem -noout -ext basicConstraints,keyUsage
```

Ожидаемый вывод:

```text
X509v3 Basic Constraints: critical
    CA:TRUE, pathlen:0
X509v3 Key Usage: critical
    Certificate Sign, CRL Sign
```

`CA:TRUE` и `Certificate Sign` разрешают этому сертификату подписывать другие сертификаты.

## 🖥️ Шаг 2. Сертификат сервера

Выпуск сертификата всегда состоит из трёх действий:

1. владелец создаёт **закрытый ключ**;
2. владелец создаёт **запрос на сертификат (CSR)** — в нём открытый ключ и поля «кому выдан», запрос подписан
   закрытым ключом владельца (так CA видит, что ключ действительно у него);
3. **CA подписывает запрос** своим ключом `ca.key` и выпускает сертификат.

**2.1. Создайте закрытый ключ сервера** (RSA, 2048 бит):

```shell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out server.key
```

| Часть команды                        | Что значит                                    |
|--------------------------------------|-----------------------------------------------|
| `genpkey -algorithm RSA`             | Создать закрытый ключ RSA в формате PKCS#8    |
| `-pkeyopt rsa_keygen_bits:2048`      | Длина ключа — 2048 бит                        |
| `-out server.key`                    | Куда сохранить ключ                           |

**2.2. Создайте запрос на сертификат сервера (CSR):**

```shell
openssl req -new -utf8 -config server.cnf -key server.key -out server.csr
```

| Часть команды        | Что значит                                                                  |
|----------------------|-----------------------------------------------------------------------------|
| `req -new`           | Создать запрос на сертификат. Без `-x509` — это именно запрос, а не сертификат |
| `-utf8`              | Читать поля как UTF-8 (кириллица)                                           |
| `-config server.cnf` | Поля «кому выдан» — из секции `[ dn ]` файла `server.cnf`                   |
| `-key server.key`    | Ключ сервера: его открытая часть попадёт в запрос, а сам запрос им подписывается |
| `-out server.csr`    | Куда сохранить запрос                                                       |

Посмотрите запрос и убедитесь, что поля правильные:

```shell
openssl req -in server.csr -noout -subject -nameopt utf8
```

Ожидаемый вывод:

```text
subject=C=RU, L=Ярославль, O=ЯрГУ им. П. Г. Демидова, OU=ПМИ-21МО, CN=Слелин Александр Владимирович
```

**2.3. Подпишите запрос сервера ключом CA** и выпустите сертификат на 825 дней:

```shell
openssl x509 -req -in server.csr -CA ca.pem -CAkey ca.key -CAcreateserial -days 825 -extfile server.cnf -extensions server_ext -out server.pem
```

| Часть команды              | Что значит                                                                                       |
|----------------------------|--------------------------------------------------------------------------------------------------|
| `x509 -req`                | На вход подаётся запрос (CSR), на выходе — сертификат                                            |
| `-in server.csr`           | Запрос сервера из шага 2.2                                                                       |
| `-CA ca.pem`               | Сертификат CA — из него берётся поле «кем выдан» (issuer)                                        |
| `-CAkey ca.key`            | Ключ CA — им подписывается новый сертификат                                                      |
| `-CAcreateserial`          | Создать файл `ca.srl` со счётчиком серийных номеров (если его ещё нет) и взять из него номер      |
| `-days 825`                | Срок действия: 825 дней (≈ 2 года 3 месяца)                                                      |
| `-extfile server.cnf`      | Файл, из которого взять расширения X.509                                                         |
| `-extensions server_ext`   | Какую секцию этого файла использовать: `[ server_ext ]`                                          |
| `-out server.pem`          | Куда сохранить сертификат сервера                                                                |

Ожидаемый вывод:

```text
Certificate request self-signature ok
subject=C = RU, L = \D0\AF\D1\80…, CN = \D0\A1\D0\BB…
```

Кириллица здесь показана кодами `\D0\AF…` — это нормально, OpenSSL так печатает UTF-8 без флага `-nameopt utf8`.

**2.4. Проверьте сертификат сервера:**

```shell
openssl x509 -in server.pem -noout -subject -issuer -dates -nameopt utf8
```

Ожидаемый вывод:

```text
subject=C=RU, L=Ярославль, O=ЯрГУ им. П. Г. Демидова, OU=ПМИ-21МО, CN=Слелин Александр Владимирович
issuer=C=RU, L=Ярославль, O=ЯрГУ им. П. Г. Демидова, OU=ПМИ-21МО, CN=Слелин А. В. Root CA
notBefore=…сегодняшняя дата…
notAfter=…дата через 825 дней…
```

Теперь `issuer` — это наш CA, а не сам сервер.

Проверьте расширения сервера:

```shell
openssl x509 -in server.pem -noout -ext subjectAltName,keyUsage,extendedKeyUsage,basicConstraints
```

Ожидаемый вывод:

```text
X509v3 Basic Constraints: critical
    CA:FALSE
X509v3 Key Usage: critical
    Digital Signature, Key Encipherment
X509v3 Extended Key Usage:
    TLS Web Server Authentication
X509v3 Subject Alternative Name:
    DNS:localhost, IP Address:127.0.0.1
```

- `Subject Alternative Name` — список имён, по которым клиент имеет право подключаться к серверу. Клиент сверяет
  хост из поля «Хост» (`localhost`) именно с этим списком. Если имени в списке нет — соединение будет отклонено.
- `TLS Web Server Authentication` (`serverAuth`) — сертификат можно использовать только для TLS-сервера.
- `CA:FALSE` — этим сертификатом нельзя подписывать другие сертификаты.

## 💻 Шаг 3. Сертификат клиента

Те же три действия, что и для сервера, но с файлом `client.cnf` и секцией `[ client_ext ]`.

**3.1. Создайте закрытый ключ клиента** (RSA, 2048 бит):

```shell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out client.key
```

| Часть команды                        | Что значит                                    |
|--------------------------------------|-----------------------------------------------|
| `genpkey -algorithm RSA`             | Создать закрытый ключ RSA в формате PKCS#8    |
| `-pkeyopt rsa_keygen_bits:2048`      | Длина ключа — 2048 бит                        |
| `-out client.key`                    | Куда сохранить ключ                           |

**3.2. Создайте запрос на сертификат клиента (CSR):**

```shell
openssl req -new -utf8 -config client.cnf -key client.key -out client.csr
```

| Часть команды        | Что значит                                                                  |
|----------------------|-----------------------------------------------------------------------------|
| `req -new`           | Создать запрос на сертификат                                                |
| `-utf8`              | Читать поля как UTF-8 (кириллица)                                           |
| `-config client.cnf` | Поля «кому выдан» — из секции `[ dn ]` файла `client.cnf`                   |
| `-key client.key`    | Ключ клиента: его открытая часть попадёт в запрос, а сам запрос им подписывается |
| `-out client.csr`    | Куда сохранить запрос                                                       |

Посмотрите запрос:

```shell
openssl req -in client.csr -noout -subject -nameopt utf8
```

Ожидаемый вывод:

```text
subject=C=RU, L=Ярославль, O=ЯрГУ им. П. Г. Демидова, OU=ПМИ-21МО, CN=Слелин Александр Владимирович, emailAddress=a.slelin.work@mail.ru
```

**3.3. Подпишите запрос клиента ключом CA** и выпустите сертификат на 825 дней:

```shell
openssl x509 -req -in client.csr -CA ca.pem -CAkey ca.key -CAcreateserial -days 825 -extfile client.cnf -extensions client_ext -out client.pem
```

| Часть команды              | Что значит                                                                         |
|----------------------------|------------------------------------------------------------------------------------|
| `x509 -req`                | На вход подаётся запрос (CSR), на выходе — сертификат                              |
| `-in client.csr`           | Запрос клиента из шага 3.2                                                         |
| `-CA ca.pem`               | Сертификат CA — из него берётся поле «кем выдан» (issuer)                          |
| `-CAkey ca.key`            | Ключ CA — им подписывается новый сертификат                                        |
| `-CAcreateserial`          | Взять следующий серийный номер из `ca.srl` (файл уже создан на шаге 2.3)           |
| `-days 825`                | Срок действия: 825 дней                                                            |
| `-extfile client.cnf`      | Файл, из которого взять расширения X.509                                           |
| `-extensions client_ext`   | Какую секцию этого файла использовать: `[ client_ext ]`                            |
| `-out client.pem`          | Куда сохранить сертификат клиента                                                  |

Ожидаемый вывод:

```text
Certificate request self-signature ok
subject=C = RU, L = \D0\AF\D1\80…, emailAddress = a.slelin.work@mail.ru
```

**3.4. Проверьте сертификат клиента:**

```shell
openssl x509 -in client.pem -noout -subject -issuer -dates -nameopt utf8
```

Ожидаемый вывод:

```text
subject=C=RU, L=Ярославль, O=ЯрГУ им. П. Г. Демидова, OU=ПМИ-21МО, CN=Слелин Александр Владимирович, emailAddress=a.slelin.work@mail.ru
issuer=C=RU, L=Ярославль, O=ЯрГУ им. П. Г. Демидова, OU=ПМИ-21МО, CN=Слелин А. В. Root CA
notBefore=…сегодняшняя дата…
notAfter=…дата через 825 дней…
```

Проверьте расширения клиента:

```shell
openssl x509 -in client.pem -noout -ext keyUsage,extendedKeyUsage,basicConstraints
```

Ожидаемый вывод:

```text
X509v3 Basic Constraints: critical
    CA:FALSE
X509v3 Key Usage: critical
    Digital Signature, Key Encipherment
X509v3 Extended Key Usage:
    TLS Web Client Authentication
```

`TLS Web Client Authentication` (`clientAuth`) — сертификат можно использовать только для TLS-клиента. Списка
`Subject Alternative Name` у клиента нет: имя хоста клиента сервер не проверяет.

## ✅ Шаг 4. Проверка всего набора

**4.1. Проверьте, что оба сертификата подписаны нашим CA:**

```shell
openssl verify -CAfile ca.pem server.pem client.pem
```

Ожидаемый вывод:

```text
server.pem: OK
client.pem: OK
```

Если вместо `OK` написано `unable to get local issuer certificate` — сертификат подписан другим CA (например,
вы перевыпустили `ca.pem`, но не перевыпустили сертификаты сервера и клиента). Повторите шаги 2 и 3.

**4.2. Убедитесь, что ключи соответствуют сертификатам.**

Открытый ключ, «вынутый» из сертификата, должен совпадать с открытым ключом, вычисленным из закрытого ключа.
Выполните две команды для сервера и сравните вывод — блоки между `-----BEGIN PUBLIC KEY-----` и
`-----END PUBLIC KEY-----` должны совпадать **символ в символ**:

```shell
openssl x509 -in server.pem -noout -pubkey
```

```shell
openssl pkey -in server.key -pubout
```

То же для клиента — вывод двух команд тоже должен совпасть полностью:

```shell
openssl x509 -in client.pem -noout -pubkey
```

```shell
openssl pkey -in client.key -pubout
```

**4.3. Посмотрите отпечатки SHA-256.** Потом их можно сверить с карточками в окне клиента и с выводом сервера:

```shell
openssl x509 -in ca.pem -noout -fingerprint -sha256
```

```shell
openssl x509 -in server.pem -noout -fingerprint -sha256
```

```shell
openssl x509 -in client.pem -noout -fingerprint -sha256
```

**4.4. (По желанию) Посмотрите сертификат полностью**, со всеми полями:

```shell
openssl x509 -in server.pem -noout -text -nameopt utf8
```

```shell
openssl x509 -in client.pem -noout -text -nameopt utf8
```

## 🧹 Шаг 5. Уборка временных файлов

Запросы `server.csr` и `client.csr` нужны были только для выпуска сертификатов — их можно удалить.

Windows (cmd):

```bat
del server.csr client.csr
```

Linux / macOS / Git Bash:

```shell
rm server.csr client.csr
```

PowerShell (файлы перечисляются через запятую):

```powershell
Remove-Item server.csr, client.csr
```

Файлы `ca.key` и `ca.srl` **не удаляйте**, если собираетесь выпускать ещё сертификаты этим же CA.

Проверьте итоговый набор.

Windows (cmd):

```bat
dir
```

Linux / macOS / Git Bash / PowerShell:

```shell
ls
```

Должны быть: `ca.cnf`, `ca.key`, `ca.pem`, `ca.srl`, `client.cnf`, `client.key`, `client.pem`, `HELP.md`,
`server.cnf`, `server.key`, `server.pem`.

## 📄 Что написано в файлах .cnf

Каждый файл состоит из секций в квадратных скобках.

### `[ req ]` — общие настройки команды `openssl req`

```ini
[ req ]
prompt             = no            # не задавать вопросов, всё берётся из [ dn ]
utf8               = yes           # значения полей — в UTF-8 (нужно для кириллицы)
string_mask        = utf8only      # кодировать поля как UTF8String
default_md         = sha256        # алгоритм хеширования подписи
distinguished_name = dn            # в какой секции лежат поля «кому выдан»
```

В `ca.cnf` есть ещё строка `x509_extensions = ca_ext` — какие расширения добавить в самоподписанный сертификат
(шаг 1.2). Для сервера и клиента расширения задаются в команде подписи (`-extensions …`, шаги 2.3 и 3.3).

### `[ dn ]` — «кому выдан» (Distinguished Name)

| Поле           | Расшифровка                  | Значение                                                         |
|----------------|------------------------------|------------------------------------------------------------------|
| `C`            | Country — страна             | `RU`                                                             |
| `L`            | Locality — город             | `Ярославль`                                                      |
| `O`            | Organization — организация   | `ЯрГУ им. П. Г. Демидова`                                        |
| `OU`           | Organizational Unit — подразделение | `ПМИ-21МО` — учебная группа                               |
| `CN`           | Common Name — имя владельца  | CA: `Слелин А. В. Root CA`; сервер и клиент: `Слелин Александр Владимирович` |
| `emailAddress` | e-mail (только у клиента)    | `a.slelin.work@mail.ru`                                          |

### `[ ca_ext ]` — расширения сертификата CA (файл `ca.cnf`)

```ini
[ ca_ext ]
basicConstraints       = critical, CA:TRUE, pathlen:0   # это CA, подчинённых CA быть не может
keyUsage               = critical, keyCertSign, cRLSign # может только подписывать сертификаты и списки отзыва
subjectKeyIdentifier   = hash                           # идентификатор своего ключа
authorityKeyIdentifier = keyid:always                   # идентификатор ключа издателя (здесь — свой же)
```

### `[ server_ext ]` — расширения сертификата сервера (файл `server.cnf`)

```ini
[ server_ext ]
basicConstraints       = critical, CA:FALSE                      # не CA
keyUsage               = critical, digitalSignature, keyEncipherment
extendedKeyUsage       = serverAuth                              # годится только для TLS-сервера
subjectAltName         = @alt_names                              # список имён — в секции [ alt_names ]
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid, issuer                           # ссылка на ключ CA

[ alt_names ]
DNS.1 = localhost
IP.1  = 127.0.0.1
```

Чтобы подключаться к серверу по другому имени (например, по имени компьютера `MY-PC`), добавьте строку
`DNS.2 = MY-PC` в `[ alt_names ]` и выпустите сертификат сервера заново (шаги 2.1–2.4).

### `[ client_ext ]` — расширения сертификата клиента (файл `client.cnf`)

```ini
[ client_ext ]
basicConstraints       = critical, CA:FALSE
keyUsage               = critical, digitalSignature, keyEncipherment
extendedKeyUsage       = clientAuth                              # годится только для TLS-клиента
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid, issuer
```

> Файлы `.cnf` сохраняйте в кодировке **UTF-8** (в Блокноте: «Сохранить как» → Кодировка UTF-8), иначе кириллица
> в сертификатах испортится.

## 🔄 Как перевыпустить сертификаты

**Перевыпустить всё с нуля** (например, поменяли ФИО или группу в `[ dn ]`): удалите старые файлы и выполните
шаги 1–5 заново.

Windows (cmd):

```bat
del ca.key ca.pem ca.srl server.key server.pem client.key client.pem
```

Linux / macOS / Git Bash:

```shell
rm ca.key ca.pem ca.srl server.key server.pem client.key client.pem
```

PowerShell (файлы перечисляются через запятую):

```powershell
Remove-Item ca.key, ca.pem, ca.srl, server.key, server.pem, client.key, client.pem
```

**Перевыпустить только сертификат сервера или клиента** тем же CA — выполните только шаг 2 (или шаг 3), а затем
шаг 4.1. Перевыпускать `ca.pem` при этом не нужно.

> После перевыпуска **перезапустите сервер** — он читает сертификаты только при старте. Клиент перечитывает их сам
> при каждом нажатии «Подключиться» / «Переподключиться».

## 🩺 Возможные ошибки

| Сообщение                                                    | Причина и решение                                                                 |
|--------------------------------------------------------------|-----------------------------------------------------------------------------------|
| `'openssl' is not recognized…` / `command not found`         | OpenSSL не в `PATH` — см. шаг 0.1                                                 |
| `Can't open "ca.cnf" for reading`                            | Команда запущена не из папки `MutualTls/certs` — см. шаг 0.2                      |
| `Could not open file or uri for loading CA private key`      | Нет `ca.key` — сначала выполните шаг 1                                            |
| Кириллица в сертификате превратилась в `Ð¡Ð»Ðµ…` или `???`    | Файл `.cnf` сохранён не в UTF-8 или забыт флаг `-utf8` — исправьте и перевыпустите |
| `unable to get local issuer certificate` при `verify`        | Сертификат подписан другим CA — повторите шаги 2 и 3 с текущим `ca.pem`           |
| `Error: no section "server_ext"`                             | Опечатка в `-extensions` или в имени секции в `.cnf`                              |
| Клиент: `Ключ … в старом формате (PKCS#1/SEC1)`              | Ключ создан командой `genrsa` (`BEGIN RSA PRIVATE KEY`). Создайте его через `genpkey`, как в шагах 1.1, 2.1, 3.1 |
| Клиент: `имя хоста не совпадает с subjectAltName`            | В поле «Хост» указано имя, которого нет в `[ alt_names ]` — используйте `localhost` или добавьте имя и перевыпустите сертификат сервера |
